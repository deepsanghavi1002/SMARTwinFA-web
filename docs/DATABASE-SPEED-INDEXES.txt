SMARTwinFA - DATABASE SPEED INDEXES (company schemas)
Written 2026-11-04. Keep this file for any new company database / schema.

WHY
  A company schema made by a migration / clone / restore has only its primary-key
  indexes. Setup SQL (grids, reports, product help) then scans whole tables for every
  row and runs very slowly. Examples: Product master 33 s -> 0.9 s; Sale Order
  Allocate 37 s -> 72 ms after the indexes.

WHERE THEY ARE NOW
  UPDATE 2026-11-04: schemas were renamed - the new SQL Server copy is now rishabh_plastic27
  (live, 64,347 ledger rows) and the previous one is rishabh_plastic27_old. Below, "_new" means the
  schema that is now called rishabh_plastic27, and "rishabh_plastic27" the one now called _old.
  Database smartwin_data, schemas rishabh_plastic26, rishabh_plastic27 and
  rishabh_plastic27_new (copied from SQL Server on 2026-11-04). The 36 indexes below
  are on rishabh_plastic27 and were copied to rishabh_plastic27_new, so both match.
  Nothing in the data is changed by an index; they are additive and can be dropped.

THE 8 "ix_" INDEXES ARE KEPT IN CODE
  .scratch/idx-all-schemas.mjs   (list "wanted"; add new ones there)
  scripts/company-indexes.mjs    (the first 3 only)
  The "rp_" indexes came with the original company schema (rishabh_plastic27); they are
  not in code. They are copied by .scratch/idx-copy-rp.mjs, which reads the definitions
  of rishabh_plastic27 and creates any that are missing in rishabh_plastic27_new.

HOW TO ADD THEM TO A NEW COMPANY SCHEMA (run from D:SMARTwinFA-web)
  1. node .scratch/idx-all-schemas.mjs            dry run, lists what is missing
  2. node .scratch/idx-all-schemas.mjs --apply    creates the ix_ indexes (every schema)
  3. Edit "from" / "to" in .scratch/idx-copy-rp.mjs, then
     node .scratch/idx-copy-rp.mjs                copies the rp_ indexes
  4. node .scratch/idx-compare.mjs                shows indexes that differ between
                                                  rishabh_plastic27 and _new

LESSONS FROM 2026-11-04
  - Indexes are built CONCURRENTLY (people can keep working). A concurrent build waits
    for every open transaction; if it times out it leaves an INVALID index of that name.
    Check:  select relname from pg_index i join pg_class x on x.oid=i.indexrelid
            where not i.indisvalid;
    Fix:    DROP INDEX CONCURRENTLY "schema"."name";  then create it again.
    (.scratch/idx-fix-invalid.mjs does this for rishabh_plastic27_new.)
  - Close DBeaver's open transactions (commit / rollback) before building indexes.
  - Run ANALYZE on the tables afterwards so the planner uses the indexes (the scripts do).
  - A new slow grid: dump its SQL, EXPLAIN ANALYZE, look for SubPlan sequential scans,
    try the index inside BEGIN ... ROLLBACK first, then add it to the list in
    idx-all-schemas.mjs and to this file.

OTHER THINGS A NEW COMPANY DATABASE NEEDS (not indexes)
  - Setup is shared and lives in schema smart_setup (not copied with a company).
  - Identity sequences: after a copy, set each sequence to max(id) or new entries clash.
  - The older SQL Server dump lost non-ASCII characters (they are literal "?"); check
    money and text columns of any new copy.
